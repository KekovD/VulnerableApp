# Python race condition fixtures

Набор исходного кода для проверки SAST-сканеров: 8 намеренно уязвимых
сценариев и 8 исправленных вариантов. Python 3.9+, только стандартная библиотека.

| ID | Файл | Что нарушается | Исправление | CWE |
| --- | --- | --- | --- | --- |
| PY-RACE-001 | `shared_counter.py` | Потеря обновления общего счётчика в потоках | Один общий `threading.Lock` на всю операцию | 362 |
| PY-RACE-002 | `inventory.py` | Два потока продают последний товар после проверки остатка | Проверка и списание под одним общим lock | 367 |
| PY-RACE-003 | `per_call_lock.py` | Каждый вызов создаёт собственный lock для общих данных | Lock хранится в объекте и используется всеми вызовами | 362 |
| PY-RACE-004 | `split_lock.py` | Lock отдельно для чтения и записи сохраняет потерю обновления | Одна критическая секция для read-modify-write | 362 |
| PY-RACE-005 | `async_balance.py` | Две корутины проходят проверку баланса до `await` и обе списывают деньги | Общий `asyncio.Lock` охватывает проверку, `await` и списание | 362 |
| PY-RACE-006 | `file_create.py` | Файл появляется между `exists()` и открытием с `w`, допускающим перезапись | Атомарное создание через `open(..., "x")` | 367 |
| PY-RACE-007 | `sqlite_withdraw.py` | Два соединения читают старый баланс и выполняют два списания | Один условный `UPDATE ... WHERE balance >= ?` | 362 |
| PY-RACE-008 | `process_counter.py` | Lock у `multiprocessing.Value` защищает отдельные обращения, а не всю операцию | Явный `with shared_value.get_lock()` | 362 |

## Эталон для сканера

В [`manifest.json`](manifest.json) перечислены все 16 вариантов. Для каждой записи:

- `id`: стабильный идентификатор сценария и варианта;
- `filePath`: путь от корня репозитория;
- `symbol`: функция или метод, к которому относится ожидание;
- `line`: строка ключевого обращения к общему ресурсу;
- `cwe`: ожидаемый CWE;
- `expectedFinding`: `true` для уязвимого варианта, `false` для исправленного;
- `executionModel`: потоки, корутины или процессы.

Маркеры `RACE: PY-RACE-...` и `SAFE: PY-RACE-...` отмечают эти строки в коде.
Одно ожидание описывает всю гонку, включая предыдущее чтение или проверку;
сканер может привязать свою находку к другой строке той же функции. Исправленный
вариант служит отрицательным контролем именно для указанной гонки.

Для сканирования выберите этот каталог. Вызовы конкурентных работников находятся
в `tests/test_race_conditions.py`; включите этот файл в анализ, если сканеру нужен
контекст запуска потоков, процессов или корутин. Эталон Python-набора хранится
отдельно от Java-эталона `src/main/resources/scanner/sast/expectedIssues.csv`.
Фактическое покрытие конкретного сканера проверяется его отдельным запуском.

## Воспроизведение

Из корня репозитория:

```sh
python3 -m unittest discover -s examples/python/race_conditions/tests -v
```

16 проверок воспроизводят нарушение инварианта в каждом уязвимом варианте и
проверяют сохранение инварианта в исправленном. Успешный тест уязвимого примера
означает, что гонка воспроизвелась: например, два инкремента дали `1`, два
списания по `80` с баланса `100` дали `-60`, либо два создателя одновременно
получили право на один файл.

Параметры `after_read` и `after_check` позволяют барьерам в тестах остановить
обоих работников после чтения/проверки. Это делает неблагоприятный порядок
выполнения воспроизводимым без случайных задержек. Ошибка остаётся в раздельных
действиях над общим ресурсом; callback не обеспечивает их атомарность.
В async-примере переключение задач происходит на `await`.

Тесты создают файлы и SQLite-базы во временных каталогах и используют метод
запуска процессов `spawn`. Для запуска не нужны сервер, Docker или сторонние
Python-пакеты. Импорт модулей сам по себе не запускает работников.

## Границы исправленных вариантов

`threading.Lock` защищает работников одного процесса, использующих один объект.
`asyncio.Lock` применяется к задачам одного event loop. Для общей памяти между
процессами нужен общий multiprocessing-lock, а для нескольких клиентов БД —
атомарная операция или транзакция на стороне БД. Пример создания файла проверяет
атомарность создания конечного имени в доверенном родительском каталоге; защиту
от подмены родительских каталогов следует рассматривать отдельно.
